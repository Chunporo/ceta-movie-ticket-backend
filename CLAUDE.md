## Commands

```bash
mvn -q clean compile                 # must be green before starting any task
mvn -q test                          # unit tests (H2, no MySQL needed)
mvn -q test -Dtest=ClassName#method  # single test
./scripts/verify.sh                  # REQUIRED before reporting done; greps forbidden patterns,
                                     # checks protected files unmodified, runs mvn clean test
IT_MYSQL_URL=jdbc:mysql://localhost:3306/ceta mvn -q -Pit-mysql test -Dtest=ConcurrentClaimTest
```

- The `it-mysql` profile in `pom.xml` runs only tests tagged `@Tag("it-mysql")` (default runs exclude them); it reads `IT_MYSQL_URL`, `IT_MYSQL_USER` (default root), `IT_MYSQL_PASSWORD` (default root). Row-locking tests need real MySQL (H2 doesn't emulate `FOR UPDATE`); local MySQL: `docker run -d --name ceta-mysql -p 3306:3306 -e MYSQL_ROOT_PASSWORD=root -e MYSQL_DATABASE=ceta mysql:8`.
- Tests must never hit real VNPay — mock `VnPayClient`.
- Report real command output, not "it passes".

## Workflow

- Work is driven by `TASKS.md` (T0–T10, strict order, gates). Each task has a prompt in `prompts/Tn-*.md`; do exactly one task per session and one commit per task. T0–T10 are done (Gate A passed); no task is queued (no open task; see the project memory for remaining gaps). Authorization: every controller endpoint carries `@PreAuthorize` (enforced by `ControllerAuthorizationRuleTest`), `SecurityConfig` ends in `anyRequest().authenticated()`, and `AuthorizationMatrixTest` lists every endpoint with its required access — add new endpoints there. `BookingSweeper` (every `app.booking.sweeper-interval`) calls `BookingExpiryService`, which locks bookings before seats (same order as payment callbacks). `app.booking.hold-enabled=false` is the kill switch: booking creation claims nothing and the payment use case claims AVAILABLE→SOLD via `InventoryService.claimAndSell`; the sweeper then leaves seats alone, so drain PENDING bookings before flipping it back. Refunds go through `RefundService` (`/api/v1/admin/refunds`); `enqueue` takes the booking row lock first and is idempotent per booking. Payment callbacks go through `service/payment/ApplyPaymentResultUseCase` (IPN `/api/v1/payments/vnpay/ipn`, return `/api/v1/payments/vnpay/return`). `POST /api/v1/payments/vnpay/create-url` (`PaymentUrlService`) creates one `payment_transaction` per attempt (`txn_ref = bookingId_attemptNo`) and the signed VNPay URL. The pre-hold `/api/bookings/checkout` and `/api/payment/vnpay/callback` were removed; a paid booking publishes `BookingCheckedOutEvent` (confirmation email after commit). `GET /api/bookings/my-bookings` is the only old-style booking endpoint left. New booking API lives under `/api/v1/bookings` (`BookingV1Controller` → `BookingCreationService` / `BookingLifecycleService`); the legacy `/api/bookings/checkout` flow is still present and predates the hold model.
- Schema changes go in a new Flyway migration (`V2__...`); never edit `V1__baseline.sql`. `ddl-auto` must stay `validate`.
- If the baseline looks wrong or incomplete, stop and report rather than deciding.
- Don't commit `application-local.properties`, `*.jks`, `build.log`, `target/`. Adding dependencies requires asking first.

## Architecture

Single Spring Boot 3.4 / Java 21 monolith (base package `com.movie.ticket_booking`), MySQL 8 + Flyway, Redis for read caching only (never locks or source of truth), JWT, VNPay, config in `application.properties` (+ `application-dev.properties` for Swagger/SMTP).

The core design is **seat inventory with hold** (BASELINE D-01..D-08):

- `service/inventory/InventoryService` is the only code allowed to touch the `showtime_seat` table. `claim` locks the `showtime` row (`SELECT ... FOR UPDATE`) then does `UPDATE ... WHERE status='AVAILABLE'` and requires affected rows == n (all-or-nothing, else 409 with conflicts). `release`, `promoteToSold`, `releaseExpired` (sweeper) complete the lifecycle. These methods join the caller's transaction so booking status changes commit atomically with seat changes.
- The boundary is enforced by ArchUnit (`architecture/InventoryBoundaryTest`): no class outside `..service.inventory..` may depend on `ShowtimeSeatRepository`. Booking/payment code must go through `InventoryService`.
- Booking flow: create booking (total price frozen at creation, never recomputed) → seats `HELD` for 10 min → VNPay IPN (primary) / return URL (same use case) → idempotent via `payment_transaction.processed_at` → tickets issued; sweeper (every 20s) expires holds. Late IPN → `refund_queue`.
- Seat map and live updates: `GET /api/showtimes/{id}/seats` reads statuses from `InventoryService.seatStatuses` (HELD/SOLD/AVAILABLE, never hold times). Every inventory change publishes `SeatStatusChangedEvent`; `SeatBroadcastListener` sends it after commit to STOMP `/topic/showtime/{id}/seats` (`{seq, showtimeId, at, seats[{seatId,label,status}]}`, architecture 8.5). STOMP CONNECT needs a bearer token (`StompJwtInterceptor`). A showtime only works if it has `showtime_seat` rows: `ShowtimeServiceImpl` and `DataSeeder` call `InventoryService.initializeShowtime`; any new code that creates showtimes must do the same.
- Tickets: `GET /api/v1/tickets/my?page&size` and `GET /api/v1/tickets/{id}` (`TicketQueryService`; someone else's ticket is a 404). Each ticket carries `qrPayload` = `CETA1.<ticketId>.<expiry>.<HMAC>` from `TicketQrService` (secret `app.ticket.qr-secret`, falls back to `app.jwt.secret`; expiry = showtime start + 2h). `TicketQrService.verify` is what staff check-in (T10) must use.
- Booking limits: `POST /api/v1/bookings` refuses with 429 `TOO_MANY_ATTEMPTS` once a user has `app.booking.max-attempts-per-showtime-per-hour` (default 3) bookings of any status for the showtime in the last hour.
- Staff check-in: `POST /api/v1/admin/tickets/check-in` `{qr}` or `{code}` (ADMIN role; staff are web-admin users, D-19). One conditional UPDATE (`checked_in_at IS NULL`) decides the winner; window opens `app.ticket.checkin-opens-before` (60m) before the show and closes 2h after its start. Columns added by `V3__ticket_checkin.sql`.
- Showtime cancellation (D-22): `POST /api/v1/admin/showtimes/{id}/cancel` `{reason}` (ADMIN, reason mandatory; `ShowtimeCancellationService`, migration `V4__showtime_cancellation.sql`). Step 1 flips `showtime.status` to CANCELLED with one UPDATE (never lock the showtime row before a booking row: booking creation holds its booking then the showtime, so that order deadlocks); `InventoryService.claim` then refuses it with 409 `SHOWTIME_CANCELLED`. Step 2, one transaction per booking (booking locked first): PENDING -> CANCELLED (hold released), PAID -> REFUNDED + `refund_queue(SHOWTIME_CANCELLED)` + cancellation email after commit. Calling it again resumes unfinished bookings and keeps the first reason. No push channel exists in the backend, so only the email half of D-22 is built.
- Gate C (BASELINE section 9) is automated in `GateCIncidentRehearsalTest` (`it-mysql`): lost IPN then return URL plus IPN retries, IPN after the hold lapsed (refund queued), app killed mid-payment (sweeper frees seats), two users one seat, manual refund of a late payment. The test ages holds in the DB (`holdTimesOut`) because inventory reads the real clock, not the sweeper's `now`. The real-money Gate B is not automated.
- Customer cancel of a PAID booking (D-15): `POST /api/v1/bookings/{id}/cancel` (`PaidBookingCancellationService`, owner only, allowed until `app.booking.cancel-before` (60m) before the show, refused once any ticket is checked in). One transaction, booking locked first: PAID -> REFUNDED (never CANCELLED), `refund_queue(CUSTOMER_CANCEL)` for the admin to pay back by hand, seats SOLD -> AVAILABLE via `InventoryService.releaseSold`. Errors: 409 `BOOKING_NOT_CANCELLABLE`, `BOOKING_NOT_CANCELLABLE`, `TICKET_ALREADY_USED`. `CheckInServiceImpl` locks the booking row (`BookingRepository.lockStatusById`) before judging it so a cancel racing a door scan cannot end refunded-and-used. `DELETE /api/v1/bookings/{id}` stays PENDING-only. Migration `V5`.
- Android contract (`docs/CETA_Android_Spec.md` section 5): auth, movies, genres and showtimes answer under both `/api/...` and `/api/v1/...` (array `@RequestMapping`; `SecurityConfig` lists both). `GET /api/v1/bookings?page&size` is the paged history (PENDING rows show their snapshot seats); `GET /bookings/{id}` also returns `id, movieTitle, roomName, startTime, refundRequired` (a refund_queue row not yet DONE). `GET /movies` takes `q, genre (slug or name), status` and optional `page,size` (still a plain list; total in `X-Total-Count`); `GET /showtimes?date=` is the cinema's local day (`app.timezone`). Error codes follow the app spec: `MAX_SEATS_EXCEEDED`, `SHOWTIME_CLOSED`, `BOOKING_NOT_CANCELLABLE` (any cancel refusal; the message says why).
- Accounts (migration `V6`): 5 consecutive wrong passwords lock the user for `app.auth.lock-duration` (423 `ACCOUNT_LOCKED`, `retryAfterSeconds`); the counter is one atomic UPDATE (`registerLoginFailure`: `locked_until` is assigned before the counter because MySQL evaluates SET left to right) and `login` is `noRollbackFor` so the count survives the 401. `POST /auth/forgot-password` always answers 202 (60s cooldown per user, emails a one-use link built from `app.auth.reset-link-template`; only the SHA-256 of the token is stored) and `POST /auth/reset-password {token,newPassword}` revokes all refresh tokens. `PATCH /auth/me {username}`, `PUT /auth/me/password` (revokes all refresh tokens) and `DELETE /auth/me {password}` (cancels PENDING bookings, refuses with 409 `HAS_ACTIVE_TICKETS` while a PAID booking's show has not ended, then anonymises the row to `deleted-<id>`; bookings and tickets are kept). Passwords are at least 8 characters.
- Notifications (S14, migration `V7`, orders only in v1): `GET /api/v1/notifications?page&size`, `GET .../unread-count`, `PUT .../{id}/read`, `PUT .../read-all` (someone else's id is 404). Rows are written by `NotificationListener` after commit from `BookingCheckedOutEvent` (ORDER_PAID), `RefundQueuedEvent` (REFUND_PENDING, skipped for SHOWTIME_CANCELLED refunds), `RefundCompletedEvent` (REFUND_DONE) and `ShowtimeCancelledRefundEvent` (SHOWTIME_CANCELLED), plus `ShowtimeReminderJob` (SHOWTIME_REMINDER once per PAID booking within `app.notification.reminder-before`). The unique key (user, type, booking) makes every producer idempotent; `NotificationWriter` inserts one row in its own transaction and a duplicate or lock conflict means "already there" (the `INSERT ... SELECT ... NOT EXISTS` form deadlocked under concurrency on MySQL). Copy is Vietnamese, the app localises by `type`. Push is only the `PushSender` seam (`LoggingPushSender` logs); FCM needs a new dependency and device-token storage, so ask first.
- Kill switch `app.booking.hold-enabled` (plus `hold-ttl`, `max-seats-per-booking`, `sweeper-interval`) falls back to claim-at-IPN.
- Errors are `BusinessException(code)` / `SeatConflictException` rendered by `GlobalExceptionHandler` as `{code,message,details[]}`; `code` strings are fixed by BASELINE §7.
- The repo is mid-refactor: the old seat-hold layer was removed (T0) and `verify.sh` fails if `SeatHold`/`SeatReservationService`/`holdSeats` reappear. Some packages named in AGENTS.md (e.g. `security/`) may not exist yet — check before assuming.
- Tests: `migration/` (Flyway baseline + entity persistence), `architecture/` (ArchUnit), `controller/` (web slice), `exception/`.
